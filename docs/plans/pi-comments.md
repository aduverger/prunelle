# Pi comment interaction simplification

Status: implemented locally after M4 (`c1b0c78`, PR #11), on `simplify-pi-comments`. Not deployed or published by this task. D13 supersedes M4's routine explicit Ask Pi/structured reply interaction. The subsequently approved [server-side queue](pi-comment-queue.md), D14, supersedes this ledger’s no-queue behavior; the verification below records the earlier interaction phase.

## Accepted intent

- Posting a desktop discussion or reply saves it and asks the attached existing Pi conversation by default, without a second Ask Pi click or routine preview.
- Include exactly the selected captured line/range, with file/repository/side/line/revision/blob identity. **No surrounding code.** A selection consisting of `)` stays exactly that selection; Pi may request more captured context if necessary.
- Include earlier thread messages for follow-ups, not the entire review graph. First comments need no history/context tool call just to see their selection.
- Pi answers normally. The extension, not the model, routes the answer back to the canonical invocation/discussion. Do not scrape terminal output or attribute unrelated responses by timing.
- Preserve existing live-conversation permissions/trust, human-only invocation initiation, original anchors, canonical IDs, committed replay, deletion protection and independent drafts. Explanation is not authorization to implement. Prepare review still uses validated structured publication; implementation remains a separate explicit saved-decision action.
- Missing/busy/unavailable Pi must not lose the saved comment, silently queue work, or trigger automatic retries. Uncertain delivery/publication must remain visibly uncertain.

## Existing owners and implementation

- `server/internal/review/agent_invocations.go`: the existing DISCUSS creation transaction assembles its saved prompt from the canonical discussion. `discussionPrompt` includes stored `SelectedText` rather than fetching live files or expanding source ranges. Follow-up history stops before the explicitly selected message, so later saved messages are not folded into an earlier request. No schema or wire-contract change.
- `client/src/Discussions.tsx`: successful saves invoke delivery separately from the comment/reply write. Draft clearing still depends only on successful save. Per-message delivery status replaces the routine Ask Pi control.
- `client/src/Agents.tsx`, `App.tsx`: a review-owned comment-delivery controller retains each saved message's exact target/revision/payload/key independently of other drafts. The existing invocation API, SSE-driven query invalidation, integration panel and exceptional dispatch previews remain authoritative; no worker or persistent outbox. Already-saved messages are not automatically sent when mounting/reloading/reconnecting.
- `integrations/pi/src/index.ts`: extension 0.4.1 keeps Pi 1.5.1 and the existing protocol. Normal DISCUSS/IMPLEMENT responses are collected through supported SDK lifecycle events and submitted only after `agent_settled`. Remove the model-facing `prunelle_reply` tool; keep context/history tools and structured `prunelle_publish_review` generation.
- README/setup and D13 explain default desktop dispatch, optional manual connect, failure behavior and the unchanged explicit CLI/API boundaries.

## Decision ledger — least confident first

1. **Desktop posting, not a hidden API side effect.** Apply default dispatch to both new discussion and reply forms. Direct API writes remain storage-only; the CLI still uses `agent ask`. This preserves existing imports/integrations and prevents agent replies from recursively triggering work. If asking were free: whether another human-facing client should adopt the same save-then-dispatch behavior. No new API flag or automatic server dispatch was inferred.
2. **Use the discussion's original revision.** A reply automatically targets its thread's captured revision, not whatever revision the reviewer happens to have selected elsewhere. Capture/navigation cannot retarget its request. If asking were free: whether an explicit future “compare with current” action is wanted; none was added.
3. **All preceding message bodies, no relevance heuristic.** Follow-ups include author-labelled prior bodies in saved order; exclude messages after the chosen input and unrelated review metadata. No summarizer, model-generated relevance filter, history cache or truncation rule was introduced. Long threads can therefore produce longer prompts. If asking were free: whether a bounded recent-history window is preferred later.
4. **Final means a complete, settled assistant answer.** Retain only the last assistant message of the final low-level run with `stopReason=stop`; publish text blocks, not thinking/tool/progress output. Empty, truncated, error and aborted outcomes do not publish. Wait through retries/continuations for `agent_settled`, retaining the existing exact custom-message/model/session correlation. New user/custom messages invalidate attribution conservatively. IMPLEMENT summaries use this same path; generation retains its structured tool.
5. **Recovery remains deliberate.** Lost dispatch responses retain the exact original key/payload and expose an unchanged retry. Definite failures and older unsent messages offer the existing target preview; UNKNOWN invocations warn before asking again. Comment saving is independent of dispatch, and no failure rolls it back. State is review-lifetime memory, not a persistent outbox; refresh/navigation warnings and server history support inspection, not execution replay. Failed request-history reads show status unavailable rather than falsely labelling existing requests unsent or offering another dispatch.
6. **Completion uncertainty is not model failure.** On unconfirmed answer publication, report UNKNOWN and warn in Pi; retain the normal answer in Pi's own history without automatic retry. Deleted invocations return 404 and release the active request instead of recreating data. Existing server completion hashing/deduplication remains unchanged.
7. **Coordinated local upgrade, no migration.** Rebuild/restart the server for richer prompts, rebuild the desktop for default posting, and `/reload` the installed local extension for automatic answer routing. Version 0.4.1 distinguishes the extension behavior. No production install, registry publication or user-session reload was performed.
