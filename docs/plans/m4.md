# M4 — Direct Pi integration and generated feature reviews

**Status: implemented and locally verified on `m4-plan`, following the owner's authorization.** Base: `7bb5504`, [M3 PR #10](https://github.com/aduverger/prunelle/pull/10), merged. Final browser suite: 35/35; Linux native Pi/review smoke passed. See §§14–16 for choices, initial failures and release prerequisites. Not merged, published or deployed.

Sources: [original specification](../Prunelle_Architecture_Implementation_Spec_2026-11-05.md) §§4.2, 6.4–6.5, 8 and M4; [D1–D12](../decisions.md); [M3 boundaries and ledger](m3.md). D12 and this plan supersede the original Rex/runtime-backend requirement and the earlier M4 draft's forks and topic-acceptance workflow.

## 1. Agreed product direction

1. **Use the existing Pi conversation.** Questions, generation and deliberate implementation requests go to the attached conversation. No fork now. A future setting may create one fork per review; do not implement that setting, a fork per discussion, or speculative fork infrastructure in M4.
2. **Keep long discussions identifiable.** Reuse Prunelle's existing `discussion_id` end to end. Give each request a distinct `invocation_id`; Pi can look up discussion history by ID instead of receiving a copy of every past message on every turn.
3. **Attach automatically when unambiguous.** No matching connected Pi: leave unattached. One matching conversation: attach visibly and allow correction. Multiple matches: ask the user. Never silently replace an existing binding or undo an explicit user choice.
4. **Generate the feature map first.** The first analysis task is to produce topics, explanations and source associations from captured changes, not attention scores or automatic bug findings. This is a task for the attached Pi, not another agent/provider framework.
5. **No topic-acceptance queue.** An explicit **Prepare review** action authorizes publishing generated review content directly after validation. A topic is navigation/explanation, not a verdict. Human content and grouping must not be overwritten.
6. **Remove Rex completely from Prunelle.** Remove its adapter and the runtime-backend scaffolding, configuration, CLI/API/UI, tests and stored runtime associations. Pi can still run inside Rex, a shell or any other host; Prunelle does not manage that host.
7. **Use the existing server connection.** A Pi extension connects outward to Prunelle's existing authenticated HTTP API. No additional listener, Unix socket, Pi daemon, credential or CORS exception.

Merely attaching Pi, posting a comment or saving a verdict sends no work. Asking a question, generating review content and sending an implementation request are separate explicit actions. Reviews remain fully usable without Pi or model credentials.

## 2. End-to-end slice

```text
Existing Pi conversation + companion extension
             │ registration, requests, correlated results
             ▼
Existing Prunelle Go API / SQLite / committed review events
             ▲
             │ review, discussion and generation actions
       MyGo desktop / CLI
```

Example: after capturing an asynchronous-upload feature across API, worker and frontend repositories, **Prepare review** asks the attached Pi for a structured feature map. It creates topics such as background processing and status reporting, explanations, and links to the relevant stored source. Selecting those topics opens the existing Text/Code/Evidence views. Nothing is approved and no project file is changed by Prunelle.

The reviewer posts a question on a topic/code/finding thread, then explicitly asks Pi to answer it. Pi receives the discussion ID and new question, retrieves missing history when needed, and publishes an attributed reply to that exact thread. A saved REQUEST_CHANGES decision can separately be previewed and deliberately sent as implementation work. The reviewer manually captures and re-reviews afterward.

## 3. Extend existing owners

- `review/reviews.go`, `revision_state.go`, `read.go`: immutable captured source, coherent selected-revision graphs and current-only semantic writes. Live coding history/worktree observations cannot masquerade as the selected stored revision.
- `review/discovery.go`: canonical source paths, `Review.ContainsPath`, repository membership and optional container context. Reuse that domain scope for cwd matching; do not introduce a workspace registry or a second UI-side path predicate.
- `review/discussions.go`: canonical discussion/message identities and reply/version/event rules. `GET /v1/discussions/{discussionId}` already retrieves history with an ETag; no second thread namespace or full coding-history mirror is needed.
- `review/manifest.go`, `topics.go`, `source_topics.go`: existing structured-content validation, canonical IDs and many-to-many source ownership. Extend their transactional mechanics for generated publication, not a parallel graph or sequence of partially successful public writes.
- `review/decisions.go`: immutable human decisions and exact actionable finding/discussion IDs. Decision creation remains independent from dispatch.
- `httpapi/auth.go`, `idempotency.go`, `events/`: authentication distinct from attribution, committed replay and durable refetch notifications. Existing readers/controllers remain authoritative.
- `agents/agents.go`: an unused semantic-adapter sketch. Adapt or replace it with the minimal proven Pi bridge; no compatibility layer, generic provider registry or unused history API is required.
- `sessions/`, `sessions/rex/`, runtime HTTP/CLI and `client/src/Sessions.tsx`: retirement targets, not dependencies to keep beneath the new bridge.

## 4. Pi connection and automatic attachment

### Registration and availability

The optional extension explicitly connects to a configured Prunelle server and reports the actual logical Pi session ID, cwd, extension/protocol version and current readiness. It uses Pi's supported session/event/message APIs, not terminal scraping, process-name inference or a new RPC subprocess. A Pi session switch changes the reported logical identity; a terminal is never the identity.

A connected extension makes the conversation discoverable. A lost connection means unavailable/unknown to Prunelle, not proof that Pi stopped. Keep credentials/model access in Pi. Continue `Prunelle-Agent: pi:<actual-session-id>` attribution under existing Tailscale/loopback authentication; the header is not a new security credential.

### Matching and user control

- Compare canonical cwd against the review's existing repository/container-context scope through the review domain. Count logical conversations, not transport reconnections.
- Automatic matching requires a common filesystem namespace: identical path strings on different machines are not a match. The initial automatic path is co-located Pi/server checkouts; unknown/remote namespaces require explicit selection rather than guessed mappings.
- With no binding/user override: zero candidates leaves the review unattached, exactly one attaches, multiple candidates require selection. Busy is execution readiness, not a reason to silently choose another conversation.
- Show the attached conversation and whether/how it was selected. Manual selection or deliberate disconnection takes precedence and survives refresh/restart; auto-discovery must not immediately undo it.
- An offline or switched-away bound conversation remains the identified target until deliberately changed. New candidates do not silently inherit an old binding or its in-flight requests. One Pi conversation may be attached to several reviews; attachment is not implementation authorization.

Use only the minimal state needed for the association and explicit user override. Do not add a general host registry, remote path mapper, heartbeat/lease framework or runtime backend.

## 5. Discussion and implementation requests

### Discussion

Use the existing comment/reply path to save the question. **Ask Pi** references that message rather than creating a second copy. The request carries the canonical review/discussion/message IDs, an invocation ID, the attached Pi identity and the requested captured-revision context. The discussion's original anchor/revision remains intact even when the question compares it with a later selected revision.

Provide a narrow discussion lookup tool using the existing GET endpoint. Send the new question and identifiers, not the whole thread on every request. Pi can recover context by ID after compaction or interleaved discussions; IDs do not themselves guarantee that the model remembers old text. Prunelle remains the source of truth for discussion history.

Return replies through an invocation-aware structured extension tool/API. Validate that the supplied discussion/review/session belongs to that invocation, and append through the existing message domain with actual AGENT attribution and invocation linkage. Never choose the destination from terminal timing, response order or free-form text. Final reply publication is idempotent per invocation; streaming tokens are not separate persisted messages.

### Implementation

Only an explicit human **Send implementation request** action dispatches a saved REQUEST_CHANGES decision. Preview its exact revision, notes, actionable IDs, original anchors and target conversation. State that implementation runs in Pi's live working environment, which can differ from the captured source.

Normal Pi instructions/permissions and tools remain in effect. M4 does **not** claim that an explanation request runs in an enforced read-only sandbox. Distinguish DISCUSS, PREPARE_REVIEW and IMPLEMENT in the protocol/instructions; an explanation request does not authorize implementation. Do not globally change Pi's tools, interrupt another task or replace its session to enforce a new sandbox.

Initially allow one active Prunelle request per Pi conversation and reject busy/unavailable targets. The extension rechecks readiness before starting; no steering, follow-up queue or automatic waiting. Supported Pi run/completion semantics must distinguish accepted, replied and settled work. Unrelated local input/session changes cannot be mistaken for the requested reply.

Sending or finishing implementation does not automatically resolve findings/threads, submit a verdict, capture source, commit, publish or deploy. Existing authorization boundaries still apply.

## 6. Prepare review — direct, non-destructive generation

### Scope and output

The action uses the attached Pi and selected current captured revision. It reads captured changes plus available coding context and produces structured topic titles/explanations and canonical source associations. The intent is a feature map, not a folder listing, attention-only analyzer, general correctness reviewer or numerical quality score.

For the first slice, generation is **additive over currently unassigned, evidence-derived source**. A fresh review naturally exposes its initial source this way. Existing topic titles, summaries, hierarchy, order, links and representations are not regenerated. Existing canonical topic IDs may be referenced for additional eligible file associations; never reconcile identities by title or manifest-local key.

Explicit source assignments, including deliberate empty sets, are protected. Existing generated source assignments are not implicitly treated as permission for later regrouping either. Files that cannot be understood from available stored content stay visibly unexamined/unassigned. Never fabricate code-range evidence for empty/binary/omitted files or fill missing representation types merely for completeness. All Source Changes remains exhaustive.

This deliberately does not promise full automatic regeneration after every capture. M3 keeps existing content/history, and questions can discuss new revisions. A future refresh of existing explanations requires its own ownership/update semantics; do not hide a three-way merge or fuzzy upsert inside this milestone.

### Publication

The extension submits a constrained structured result correlated to the original invocation/revision. Reuse the existing manifest vocabulary, validation and ID resolution wherever it fits. Use canonical file-topic assignment mechanics when grouping is not a precise evidence range. Keep the existing public import contract append-only and unchanged; generated publication is not a new import upsert mode.

Validate the complete result before one atomic publication transaction. In that transaction recheck:

- The review exists and the targeted revision is still the current editable one.
- This invocation has not already published successfully.
- Referenced existing topics are active canonical members of this review.
- Every affected file is still eligible with the expected mode/version and canonical membership. Derived ownership can change without an assignment-version change, so an ETag alone is insufficient.

Create new topics/explanations and source associations together, or write nothing. Use generated origin and actual Pi authorship; keep the human initiating actor separately. Interpretations are INFERRED, not fabricated test/measurement results; source citations retain their immutable IDs/revisions. Do not rewrite general provenance rules by author kind.

There is **no pending-proposal store, accept/reject state, topic approval dialog or separate application endpoint**. The explicit Prepare action is the user action authorizing publication. Malformed output, stale source/grouping or capture advance causes an explained failure, not a partial graph or silent publication to a different revision. Preserve enough request/result context to inspect that failure and explicitly retry; do not automatically retarget or apply it later.

Replaying a successful publication returns its recorded canonical result rather than creating duplicate topics. Concurrent/independent requests covering the same formerly unassigned files cannot both publish stale groups. If there is no eligible source, explain that rather than duplicating the feature map.

## 7. Minimal persistence and failure handling

Add a migration after 0006 for only the required Pi data and Rex retirement:

- **Agent session:** Prunelle ID, logical Pi identity, reported version/cwd and connection availability. Store no complete global coding transcript or runtime linkage.
- **Review binding:** selected agent plus the minimal automatic/manual/disconnected choice needed to preserve user intent.
- **Invocation:** owning review, intent, requesting actor, original discussion/message or decision, context revision, target Pi, correlation, status/error and durable result references. Generation also records actual producer/model/schema version, input scope/fingerprint and resulting canonical IDs.
- **Reply linkage:** associate an invocation with its committed discussion message so duplicate completion cannot create another reply.

Use generation metadata on the invocation rather than a second AnalysisRun/proposal lifecycle unless a concrete need emerges during implementation and is explained first. Reusing an identical completed generation is a lookup of owned results, not a new cache service; input identity must include all supplied source/scope/semantic context and actual producer/model/prompt identity. A cached result is not a claim that new analysis occurred.

Persist an invocation before live dispatch, but do not turn it into a durable execution queue. Reuse POST receipts for initiating actions and publication; replay never sends work again. Conditional association changes follow existing ETag/If-Match conventions. After disconnect/restart, represent definite failure versus uncertain delivery/completion honestly. Do not resend commands on transport reconnection or automatically retry writes. Matching late results may finish only their original extant invocation; duplicates and conflicting completions cannot create new content.

A binding/selection change never retargets in-flight work. Review deletion purges owned bindings, invocations, outputs, reply linkage and private receipt/event data under existing rules. Shared agent identities/other reviews survive; late results cannot recreate deleted records. Do not stop Pi/Rex processes, delete project files or erase user-owned Pi history. No review-private transcript sidecars outside owned storage.

## 8. Complete Rex/runtime retirement

Prove the direct Pi round trip before removing the old integration, then remove it within this milestone rather than keeping two discovery paths:

- Delete `server/internal/sessions/`, including Rex, generic runtime/backend types, observers, fake/contract fixtures and unsupported future-backend placeholders.
- Remove session-service startup/shutdown wiring, CLI runtime/backend commands, HTTP runtime/backend/association routes and OpenAPI/generated DTOs.
- Replace the runtime-session UI with Pi connection/selection information and actions. Remove runtime polling, not merely hide its panel.
- Retire `[[session_backends]]` configuration. Reject it with removal/Pi-setup guidance, following existing retired-config handling; do not silently ignore it or keep an unused compatibility path.
- Drop `review_runtime_sessions`, `runtime_sessions` and `session_backends` through a new migration. Preserve released migrations 0001–0006 unchanged and verify upgrades that pass through their intermediate schemas.
- Do not translate Rex block/runtime links into Pi bindings: their logical conversation identity is unknown. Use actual Pi registration and the new matching/user-selection rules.
- Remove obsolete deletion queries, stale runtime assertions/fixtures, generated imports and fake-Rex setup in browser/native tests. Preserve independent source/history/deletion contracts.
- Update README/config examples, CLI help, current plan/status and decision references. Keep earlier milestone plans/specification as history, clearly superseded by D12 rather than pretending Rex was never implemented.

The only lost capability is independent terminal/process observation when Pi is disconnected. Report Pi connection unavailable/unknown instead; do not infer process death. Do not uninstall, configure, launch, stop or otherwise modify the user's actual Rex application or sessions.

## 9. Client, CLI and protocol slice

- Integrations shows the actual attached Pi conversation, cwd, selection provenance and ready/busy/unavailable state. Offer selection/disconnection when needed; no terminal control, model administration or general chat screen.
- Add **Ask Pi** to existing discussion/message context, **Prepare review** for eligible captured source and **Send implementation request** on a saved actionable decision. Display original versus requested source context honestly.
- Preserve review-lifetime code/reply/decision/correction drafts. Keep invocation retry identity separate from message submission; a dispatch failure cannot repost an already saved question. Late refresh/results cannot replace the selected revision or dirty drafts.
- Add the minimal CLI equivalents for list/select/disconnect, generation, discussion requests, invocation inspection and deliberate implementation handoff. Preserve invocation-cwd semantics and attribution; do not expose arbitrary command execution.
- Define registration/live stream, action, lookup and correlated completion contracts in OpenAPI with generated Go/TypeScript consumers. Connect the extension to the current authenticated listener using ordinary HTTP and a cancellable server stream; no new endpoint listener or secret.
- Durable review SSE remains state notification. Any live dispatch channel must not replay execution commands after reconnect/restart. Exact route names/framing are mechanisms finalized by the capability checkpoint, not new product requirements.

## 10. Implementation order and stop-gates

1. **Disposable Pi bridge checkpoint.** Use the supported extension API against the actual tested Pi version: registration, idle-only send, stable discussion lookup, structured correlated reply and settled-run behavior in the same conversation. No RPC child/terminal scraping/fork. Verify session switching, disconnect/late results and that unrelated local input cannot be misattributed. Use disposable harness/provider fixtures, not the user's active coding session.
2. **Pi state and association.** Add the new owned records, connection lifecycle and canonical zero/one/many attachment with authoritative manual override. Preserve old review data and source identities.
3. **Discussion vertical slice.** Existing saved question → invocation → real extension → one attributed reply on the original discussion. Prove duplicate/unknown-outcome/restart/deletion behavior before broad UI work.
4. **Prepare review publication.** Snapshot/context lookup → structured generation → one non-destructive canonical publication. Prove rollback, eligibility, capture races and replay before adding the action to the desktop.
5. **Rex retirement.** Remove all §8 surfaces and migrate retired runtime data; the Pi path must work without Rex installed. Do not retain a generic runtime layer for hypothetical future providers.
6. **Explicit implementation handoff and UX/CLI.** Exact saved-decision preview → deliberate dispatch to the attached idle Pi. Keep ordinary comments/decisions passive and existing draft controllers stable.
7. **Documentation and complete affected verification.** Update installation/upgrade instructions, API/events and this ledger. One milestone PR unless actual implementation size warrants a separately proposed split.

A missing supported Pi capability is a stop-and-report point. Do not substitute session replacement, automatic steering, a new daemon, paid provider use or managed agent launching without approval.

## 11. Durable validation and rollout

Use disposable real Git/storage/API fixtures and controlled Pi extension/provider fixtures. Ordinary tests must not touch user worktrees, active sessions or paid credentials. Prefer observable runtime/protocol contracts over private structure counts or exact prompt prose.

- **Attachment:** canonical review scope, zero/one/multiple sessions, manual selection/disconnection across refresh/restart, unavailable bound targets, session switches and remote/unknown path namespaces. Shared Pi use across reviews does not merge review state or authorize work.
- **Thread identity:** two discussions with interleaved history and distinguishable correlated results; on-demand lookup after context loss; out-of-order results from different sessions or late completion. Wrong thread/review/session IDs reject, duplicate completion appends exactly one reply and ordinary comments send nothing.
- **Same conversation:** actual extension APIs preserve the Pi session identity and existing conversation. Busy requests do not steer/queue; session/local-input changes cannot produce a falsely correlated answer. Do not write a test claiming an enforced read-only sandbox.
- **Generation:** visible feature-level topics/explanations from real captured source, actual canonical file associations, direct publication without approval UI, unchanged manual metadata/empty assignments, and no invented evidence. Malformed/cross-review/stale outputs write nothing; derived ownership changes without ETag changes still reject; concurrent publication/capture and dropped responses cannot duplicate or retarget output.
- **Implementation authorization:** saved verdict creation alone dispatches nothing; explicit human action carries exact actionable IDs/revision/target. Busy/offline/unknown cases do not auto-dispatch, resolve concerns, capture or publish.
- **Persistence/deletion:** existing actor/login attribution, ETags, committed replay, resumable review SSE, history and hard-deletion protections cover new owned data. Late completion cannot resurrect deletion or harm another review/shared source.
- **Retirement:** active runtime code/API/CLI/config/polling is gone. Old runtime configuration fails with guidance; new installation and separately verified v6 upgrade preserve canonical review/source data while retiring runtime rows. No actual Rex installation is accessed.
- **Desktop/native:** real-server question/reply, attachment choices, generated topic navigation, implementation preview and lost-response/capture/deletion draft retention. Review-only navigation/comments/verdicts work with no Pi extension or reachable model.

Run affected Go format/generation/vet/race suites and Darwin arm64 builds; client dependency/peer/generation/format/lint/type/negative-type/model/build and desktop Go checks; extension type/behavior tests against the recorded Pi API version; full hermetic browser suite and bundled Linux MyGo/WebKit smoke. Inspect generated artifacts and separately verify real schema upgrade/backup/rollback. Do not retain one-off schema reconstruction as a permanent test merely because migration verification occurred.

A real-provider smoke requires explicit credential/cost authorization; fakes cannot establish provider behavior. Native macOS runtime/signing, live-tailnet and capacity qualification remain separate. The existing intermittent initial-source viewport failure is not a claimed M4 fix; record failures truthfully, and do not weaken timeouts/exclusions or suppress large-bundle/ResizeObserver warnings.

Release requires a stopped-server complete data-directory backup, removal of retired runtime configuration, coordinated server/CLI/desktop upgrade and explicit Pi-extension installation/version instructions. Older binaries reject the schema; rollback restores backup. No production migration, process control, paid model call or publication is authorized by preparing this plan.

## 14. Actual implementation ledger — least confident choices first

These are implementation choices where the agreed behavior left room, not additional product requirements.

1. **Additive, flat initial generation.** New generated topics are root-level navigation with a Markdown Text explanation and the existing canonical Code view. 2. **Conservative filesystem identity.** Automatic matching uses canonical local cwd and `Review.ContainsPath`. A proxied/Tailscale connection is manual-only, even if it happens to reach the same physical host. This avoids guessing host/path equivalence. If asking were free: whether same-host HTTPS discovery deserves an explicit namespace contract; no host registry or mapper was added.
3. **Three selection states.** AUTO, MANUAL and DISCONNECTED preserve deliberate no-agent selection and conditional edits. 4. **A more deliberate CLI implementation handoff.** `agent implement` defaults to a read-only preview; sending requires both `--yes` and an explicit `--agent-session` ID. Other dispatch commands are themselves deliberate actions. CLI dispatch prints its exact target/revision and retry key; unchanged retries are manual. If asking were free: whether a terminal confirmation prompt is preferred. No persistent CLI outbox or automatic write retry was added.
5. **Readiness identifies the existing context, not an isolated run.** Retain the reported model and pre-request Pi leaf ID. Reject a changed model/context before injection; unrelated input, branch/model changes invalidate active attribution. The input fingerprint is a stale-generation guard over the immutable revision identity, semantic/source projection, reported producer/context and protocol version, not a complete Pi-history mirror or cross-request analysis cache. If asking were free: whether broader cached/regenerated analysis is wanted. It is not assumed.
6. **Minimal durable identity plus a live slot.** Schema 0007 stores logical Pi identities, review bindings, invocations and reply linkage. Readiness/connections/reservations are in memory. An accepted invocation is committed before live dispatch, but no database polling worker consumes it. The original connection identity makes disconnect/restart uncertainty visible; reconnection does not execute old records. Logical agent identities are service-owned and can exist independently of a review; review-owned prompts/results/bindings/linkage/receipts are removed by deletion. Shared identities and user-owned Pi history are not erased. If asking were free: whether a separate explicit “forget disconnected Pi” control is wanted; no expiry/cleanup worker was inferred.
7. **Use existing writes, not a second analysis lifecycle.** Generated publication reuses import IDs/writer validation with GENERATED origin and the existing transactional file-topic writer. It atomically rechecks current revision, input fingerprint, eligibility and canonical ownership. Completion is hash-deduplicated per invocation, including replay after capture; conflicting results reject. Existing public import behavior stays append-only. No AnalysisRun, proposal acceptance endpoint, analyzer/provider framework or cache service was added.
8. **Exact dispatch target is part of the request.** `agent_session_id` is required in the creation payload and rechecked against the binding inside the write transaction. A selection change fails instead of retargeting. Neither action derives identity from text/timing, resolves concerns, advances source or submits a verdict.

10. **Bounded character paging.** Read tools use 1-based Unicode character windows, default 10,000 and maximum 12,000, rather than line windows over escaped JSON. File output contains raw captured BASE/HEAD text. This addresses the demonstrated inability to retrieve the tail of a long source line while keeping output below Pi's 50KB limit. No captured bytes are substituted with live worktree content.
11. **One tested SDK/package boundary.** Pin Pi 1.5.1 and the matching TypeBox dependency; extension/protocol version is 0.4.0. Use the supported existing-session extension APIs and a companion local package. Node 26 tests use erasable TypeScript syntax. Installation/reload is documented, not performed against the user's active session. Future SDK versions and a fork-per-review setting are not claimed supported.
