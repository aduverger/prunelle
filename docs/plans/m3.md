Base: `ade0646`, [review-owned repositories PR #9](https://github.com/aduverger/prunelle/pull/9), merged with successful CI. The [original specification](../Prunelle_Architecture_Implementation_Spec_2026-11-05.md), especially §§4.1–4.2 and M3, defines the intended behavior; [D1–D10](../decisions.md) and the [review-owned model](review-owned-repositories.md) supersede its workspace/SwiftUI/auth assumptions.

## 1. Outcome and boundaries

After a second capture, a reviewer can answer **what changed since the earlier revision, which findings remain open or were explicitly resolved, and which discussions still refer to older source**. Opening an older revision must not combine its code with today's topic graph.

Required behavior:

- Preserve immutable source, requested refs/resolved SHAs, repository and semantic IDs, original anchors, attribution, messages and revision-bound decisions.
- Show added/changed topics and findings, explicit finding resolution/reopening, and topic lifecycle changes. Never infer that a concern was fixed because a file, finding or topic disappeared.
- Preserve human titles, ordering, relationships and discussions when capture advances. Imports must not overwrite them.
- Make unmatched/unassigned source visible and let the reviewer correct file-to-topic associations, including many-to-many associations and deliberate unassignment.
- Keep original-revision navigation, honest unavailable states, ETags, durable SSE, committed idempotent replay and in-memory draft safety.

**Non-goals:** M4 analyzers/Pi interaction, semantic matching by title/key, automatic code-anchor relocation, rename/line-offset guessing, an inter-revision three-way diff, a general topic/diagram editor, search/filtering as a separate feature, membership editing, automatic capture/fetch/branch switching, runtime control, persistent drafts/outbox, background workers and automatic write retries. Keep Go/SQLite/WAL, React/MyGo/Pierre, API-only loopback/Tailscale and the approved filesystem trust model unchanged.

## 2. Existing end-to-end flow

The implementation must extend these owners rather than introduce a second graph or membership implementation:

- `review/reviews.go`: `CaptureRevision` collects Git outside the writer transaction, inserts immutable snapshot/blob rows, advances `current_revision_id`, then emits `revision.created`. `GetFile` already reads stored bytes, not the worktree.
- `review/manifest.go`: `Import` targets a revision, assigns fresh canonical IDs for manifest-local keys and inserts one atomic, attributed graph. Keys are not durable identity mappings, and there is no update/reconciliation import mode.
- `review/topics.go`, `representations.go`, `read.go`: topic metadata/links and representation configs are mutable current state, with ETag versions. Findings have a stored lifecycle enum but no mutation API or exposed version. Current reads do not reconstruct earlier graph state.
- `review/reviews.go`: `topicsByFile` is the canonical source-membership rule, using active topics and reachable code-range evidence. Both `SourceChanges` and code-thread topic projection consume it. `CODE_DIFF` currently selects code through evidence IDs, not arbitrary file assignments.
- `review/discussions.go`: anchor/range and messages are persistent; `anchorTopics` and diagram-element validation currently consult mutable links/configs. Those lookups also need original-revision semantics.
- `httpapi/handler.go` and `idempotency.go`: reuse the existing conditional-write and POST receipt behavior. Events are refetch notifications, not a content history from which old graphs can be reconstructed.
- `client/src/hooks.ts`: `useReview` fetches review-wide semantic lists; only source queries are revision-keyed. `App.tsx` switches the source snapshot but explicitly labels topics/explanations as current. Representation cache keys omit revision.
- `App.tsx`, `Discussions.tsx`, `CodeReview.tsx`: review-lifetime composers/controllers, original-source identities and independent retry state already exist. Preserve their lifetimes when adding revision-aware queries.

## 3. Accepted product boundary

The owner approved starting implementation after the intent review. The recommendations below define the accepted boundary; the original draft's uncertainties remain in §9 for traceability.

### A. Editable latest graph; freeze it when capture advances

Source revisions remain immutable. Semantic state for the latest source revision remains editable through imports and existing mutations. A successful next capture freezes the predecessor's complete semantic view in the same transaction that advances the review; the latest editable graph carries forward the existing human-authored state.

Older semantic views become read-only. New imports into a superseded revision are rejected explicitly, rather than changing frozen history or today's graph. Replies, thread resolve/reopen and human decisions may still target earlier revisions: they are continuing review activity, not edits to an old topic graph. Immutable old-revision code discussions remain supported.

This is smaller than versioning every keystroke/edit or introducing a proposal/event-sourcing framework. It gives a precise meaning to comparison: **the earlier revision's last semantic state before advance versus the selected later revision's state**. The latest side can still change until the next capture. If independent semantic checkpoints or historical graph editing are required, this boundary needs a different design.

### B. Keep topic lifecycle distinct from finding resolution

Recommendation: retain topic `ACTIVE`/`OBSOLETE`; expose findings `OPEN`/`RESOLVED`/`DISMISSED`, including reopening. A topic is navigational scope, not necessarily a concern that can be fixed. Show topic obsolescence explicitly; never equate it with a resolved finding or resolved discussion.

The roadmap says “resolved topics and findings.” The accepted interpretation is topic lifecycle changes plus finding resolution, not a third topic state. Any later independently resolvable topic would need its ownership/reopening semantics defined first.

### C. Conservative anchor validity, no relocation engine

Keep every discussion's original revision, ID, path, side, range, selected text and blob hash. Opening it always opens its original stored context. Against another revision:

- Same repository, exact path and side with identical stored blob: **content unchanged**; this is not evidence that the concern is resolved.
- Different content: **outdated**, with a reason; do not move the range even if its text occurs elsewhere.
- Missing stored file/side, binary/omitted data, or unavailable historical representation: **unavailable to compare**, not “deleted” or “fixed.” Only changed files are stored, so absence from a later capture is not proof of deletion.
- Diagram anchors use the original revision's representation config and stable element ID. A changed/missing element is flagged without selecting an unrelated current node.

These are derived read results, not persisted mappings, numerical confidence scores or a background job. M3 does not duplicate old inline annotations into a later CodeView. Older threads remain reachable from Comments and their owning semantic context.

### D. Honest legacy-history boundary

Pre-M3 metadata was overwritten in place; prior topic/representation versions and manifest-key mappings cannot be recovered reliably. Keep all original IDs, source, messages, decisions and existing content. Treat the current graph at upgrade as the known editable baseline; its first subsequent advance freezes it normally.

For earlier revisions without a recorded semantic view, return **semantic history unavailable** and retain source/discussion/decision access. Do not backfill today's graph into every old revision or invent old titles, links, statuses or diagram configs. An empty known graph and an unknown legacy graph must be distinguishable in the API and UI. Do not guess unavailable semantic context for a new anchored discussion or finding selection: explain the validation failure and keep its draft. Existing threads remain replyable; immutable code/review comments and source-only decisions remain supported.

## 4. Minimum domain/storage design

### 4.1 Current state plus normalized frozen history

Keep existing tables as the authoritative editable current graph. Add migration `0006_revision_review_state.sql` for normalized frozen graph state and the small additions required for finding edits and source-link corrections. Do not rewrite released migrations 0001–0005 or add another public review/workspace lifecycle.

A frozen view must preserve topic fields, hierarchy/order, lifecycle, author/import metadata and typed links; finding fields/status/evidence links; representation config/identity/version; and the membership of immutable records visible in that view. Existing immutable intent/change/evidence/attention records remain under their original IDs and revisions; references do not acquire new authors or fabricated current-revision evidence. Retain the existing JSON representation config format, not an opaque JSON dump of the core graph.

Put archive selection and read assembly in the review domain, using the existing SQLite transaction primitives. One revision-view selector chooses current state, frozen state or explicit unavailability. Comparison, original-anchor lookup and source membership use that selector; consumers must not rebuild the rules independently. Use one read transaction for each complete view/comparison, including with a single reader connection.

The archive is the historical source of truth, not a second writable graph or recomputable cache. Additive tables should not need the FK-suspension machinery specific to migration 0005. Define actual tables/constraints from the covered fields during implementation; prove complete round-trip reads before wiring the UI.

### 4.2 Atomic capture boundary and conditional edits

Inside the existing capture write transaction:

1. Read the actual current revision at commit time; do not archive a graph read before the potentially slow Git capture.
2. Freeze that predecessor's graph if one exists, then insert the new source revision/snapshots and carry forward eligible explicit file-topic corrections.
3. Invalidate pre-advance topic/representation/finding edit versions, so an old ETag cannot edit a later revision merely because its text did not change. Do not count that mechanical version increment as a semantic change.
4. Advance the current revision and emit the existing committed capture event.

Any insertion/archive failure rolls the entire operation back: no half-frozen predecessor, partial new revision, moved current pointer, leaked assignments or notification. Concurrent captures serialize through the current writer; no lease, new retry loop or duplicate capture service.

Semantic mutations must validate the targeted current revision and ETag within their transaction. Resolve an implicit current target once per command and recheck it before committing, including creates/moves/representation edits; do not silently resolve a different current revision after waiting for the writer. Imports must recheck their resolved target before committing. A stale edit returns the existing precondition/conflict behavior and leaves its draft intact, rather than applying to a newer revision. A committed idempotent request still replays its original response after advance; replay must not execute those new checks as a second mutation.

### 4.3 Identity and finding updates

Do not reinterpret manifest-local keys as global identity or fuzzy-match entities by title/path. Keep append-only imports and their existing author/provenance semantics. To retain an existing topic/finding, reuse its canonical Prunelle ID and explicitly update links to newly imported records through conditional mutations. A repeated full manifest still creates new identities; the UI must not pretend it matched them.

Add the missing finding mutation for status and explicit evidence-link replacement, with a version/ETag, revision guard, actor event and same-review validation. Keep `first_seen_revision_id`, original authorship and earlier frozen finding state. Resolution/dismissal/reopening is deliberate, never inferred from source disappearance or a new capture, and does not automatically resolve discussions or submit a decision. Follow existing authenticated-actor rules; only review decisions have the established human-only authorization restriction.

Existing topic mutation APIs remain the way to change canonical record links, titles, hierarchy and order. M3 does not add a general metadata editor or silently refresh those fields from imports.

### 4.4 File-topic corrections and one ownership rule

A reviewer must be able to assign a changed file to several existing active topics, remove a mistaken derived association, intentionally leave it unassigned, or reset to evidence-derived associations. This must also work for empty, binary and content-omitted files; do not manufacture a full-file code-range evidence record just to express grouping.

Store a revision/file-scoped explicit topic-set override with its conditional-write version. Absence/reset means evidence-derived ownership; an explicit empty set means deliberately unassigned. The canonical membership result is the explicit set when present, otherwise the existing reachable-evidence result, restricted to eligible topics in that revision. An obsolete topic claims no source, but its correction/history is not silently erased.

Only code-range evidence from the selected source revision derives ownership there; an older evidence reference is historical grounding, not a claim on today's same-named file. Expose this single result to exhaustive Source Changes, topic code selection, topic badges and discussion topic projection. Extend code-view file selection as needed to expose canonical file references alongside precise evidence ranges; an assigned binary file must not disappear because it lacks code-range evidence. Do not implement UI-only assignment or a second client-side grouping algorithm.

On capture, preserve explicit corrections only for exact repository/path identities still present in the new changed-file set. Keep human intent when contents change, with the ordinary changed-source warning; do not guess renames. Missing files' corrections remain in their historical revision and are not automatically resurrected if that pathname returns later. Reset-to-derived must be explicit and conditionally versioned too.

## 5. Reads, comparison and desktop

### Public contract

Prefer one coherent **revision-view** read over adding divergent historical filtering to every existing list endpoint. It returns the selected revision ID, editable/frozen availability, and its topics, findings, representations and supporting semantic records. Unavailable history is a distinct result, not an empty successful graph. Keep unrelated current/history endpoints and call sites unless correctness requires changing them; reuse domain read assembly rather than a parallel implementation.

Add a comparison read between two revisions of the same review. Default the UI baseline to the immediately preceding revision; allow an explicitly selected earlier baseline. No baseline means an ordinary initial review, not an error. Require the baseline ordinal to precede the target; reject cross-review, equal or reversed pairs. Legacy-unavailable baselines disable semantic comparison with an explanation, not an invented “everything added” result.

Comparison uses stable IDs and effective field/link/config values, ignoring version counters, timestamps and ordering of set-valued links. A new view's revision ID alone does not make carried metadata “changed.” Report added, changed, unchanged and lifecycle transitions; show resolved, dismissed and reopened findings distinctly. Include changed-field reasons, not scores. Show linked-source changes separately where stored bytes are comparable; unavailable comparison is not unchanged. A topic/file disappearing from the base-ref diff does not resolve it.

Validate new semantic discussion targets and selected decision findings against the requested revision's known membership, not just the mutable review-wide ID set. A later-born finding cannot become an earlier revision's concern. Earlier threads may remain actionable in a later decision with their original anchors intact; do not require every selected discussion to originate on the decision's revision. Preserve existing historical records and handle legacy-unknown membership honestly rather than deleting or rewriting them.

Extend OpenAPI and generated Go/TypeScript contracts together. Finding and file-topic mutations reuse ETag/If-Match and existing write conventions; a lost PATCH response follows the existing reload/review/explicit-retry path, not an invented POST receipt protocol. Extend event descriptions and owned-data deletion for all new persisted rows. Preserve body-less pending retry protection and byte-identical committed POST replay.

### Desktop behavior

- Split review-lifetime data (review/revisions, discussions, decisions) from revision-keyed semantic data in `hooks.ts`. Key graph, representation, comparison and source caches by the actual revision IDs. Cancel/ignore late responses for a previous selection.
- The revision selector changes the **whole semantic view**, not just code. Label the editable latest view versus frozen earlier state and show the selected comparison baseline and change reasons.
- Reuse Topic/Findings/Files/Comments navigation. Show new/changed/lifecycle badges and explicit finding status controls; add a small file-topic selection dialog with reset-to-derived. Historical graph controls are read-only. Keep All Source Changes exhaustive rather than replacing it with only matched or changed topics.
- Carrying an older explanation/evidence reference forward does not make it current evidence: retain its source-revision label. Representation authoring revision remains provenance; starting a new diagram discussion uses the displayed graph revision and validates its config there.
- Opening any old topic, finding, code or diagram discussion switches to its **original** semantic/source revision, not the same current ID with today's contents. If historical semantic content is unavailable, keep the thread visible and explain the limitation.
- Do not key/unmount the review-lifetime composer/provider/controllers by selected revision. Code, reply and decision drafts retain their original anchors/retry identities. New unsaved link corrections also survive refresh/advance and cannot silently apply to a different revision. Guard deliberate departure/discard through the existing draft-safety path, without a generic persistent draft registry.
- SSE refresh must not switch a reviewer away from an explicitly selected old revision or erase an open comparison/form. Offline/failed refresh retains the last identified data with retry status, never relabels it as another revision.

## 7. Acceptance and regression evidence to add

Use disposable two-repository fixtures with three distinguishable source revisions, nonempty linked semantic content and actual moved/deleted/unchanged text. No live user worktree, credentials or Rex session. Test user-visible outcomes at stable seams rather than table totals, component counts or helper calls.

- **History:** change a topic title/order/link, representation node and finding status between captures. Earlier frozen reads, original diagram navigation and decisions retain their old values/IDs after later edits and restart; latest human edits carry forward. Capturing alone does not manufacture semantic changes or resolution.
- **Migration:** upgrade v5 fixtures containing rich history/shared repository IDs. Current state survives exactly; unrecoverable earlier semantic state is explicitly unavailable while old source/messages/decisions remain readable. Empty known graphs remain distinct. Ordinary FK enforcement and a clean reopen hold.
- **Atomicity/concurrency:** inject a failure after predecessor archive/source writes; neither sealing nor advance commits, and retry succeeds. Two concurrent captures preserve both revisions and the right predecessor views. Advance racing a topic/representation/finding/import/correction write either includes it in the correct predecessor or rejects the stale operation, never retargets it.
- **Read coherence:** a single-reader pool can assemble complete views/comparisons without deadlock; concurrent current edits cannot mix rows from different SQLite snapshots in one response. A cross-review/reversed comparison is rejected.
- **Semantic comparison:** explicit add/change/obsolete, finding resolve/dismiss/reopen and unchanged cases; set reordering/version bumps are not changes. Similar names/reused manifest keys never merge IDs. Omitted records or missing files never auto-resolve concerns. A future-revision entity cannot be used as an earlier discussion/decision target; an older thread can still be selected for later actionable review.
- **Source corrections:** many-to-many assignment, explicit unassignment, removing derived ownership, reset, stale ETag, lost response/reload and capture carry-forward. Topic code, Files, Unassigned and thread context agree. Include empty/binary/omitted files, obsolete topics, exact-path disappearance/reappearance and ambiguous renames.
- **Anchors:** BASE/HEAD, identical blob, inserted lines, replaced/repeated text, renamed/deleted files, a file absent only because it is unchanged, and unavailable content. Original ranges/text/hashes never change; no guessed relocation or false “fixed” label. All supported non-code anchor families resolve through their original graph or an honest legacy limitation.
- **Protocol and deletion:** committed capture/import replay is unchanged after advance/restart; rejected stale writes emit nothing. New state/corrections are purged by review deletion without damaging another review, shared blobs, project files, runtime links or late-receipt protection. SSE resume/reconnect still reveals committed mutations/deletion without replaying deleted private content.
- **Desktop:** real-server revision switching across Text/Diagram/Code/Evidence/Findings, non-adjacent comparison, original-discussion navigation, correction/status updates and legacy unavailable states. Keep code/reply/decision/correction drafts during remote capture, revision navigation, dropped responses and remote deletion; delayed responses cannot replace the selected revision. Retain native Pierre scrolling/annotation and bundled transport checks.

## 13. Workspace intent and branch simplification review

### Reviewer intent

**Goal:** safe, meaningful re-review after capture: compare semantic state and source across revisions without replacing historical context with today's graph. Preserve IDs, immutable source/refs/SHAs/code anchors, human edits, author/provenance, human-only verdicts, ETags, durable SSE, committed replay and independent in-memory code/reply/decision/correction drafts.

**Accepted behavior/tradeoffs:** latest semantic state is editable; the next capture freezes its predecessor atomically. Historical graph imports/edits are rejected, but old threads and human decisions continue. Topics stay ACTIVE/OBSOLETE; finding resolution/dismissal/reopening is explicit and never inferred from absence. Legacy missing history is unavailable, not fabricated.
