# M1 - Review mutations, concurrency, and events

Goal: a reviewer can edit topics and representations, discuss any review record or an exact code range, and submit a decision tied to a revision, all through the API. Concurrent edits cannot overwrite each other silently, retried requests do not create duplicates, and clients follow changes through a resumable event stream that survives disconnects and server restarts. API and a small CLI addition only; the client arrives in M2.

## Scope

In: topic create/edit/move, representation create/edit, discussions with typed anchors, messages, discussion resolution, review decisions, `ETag`/`If-Match`, `Idempotency-Key`, SSE at `/v1/events`, restart/reconnect tests.

Out: finding status changes (dismiss/resolve), review close, topic deletion (topics become `OBSOLETE` instead), message edit/delete, agent-authored messages and invocations (M4), re-anchoring across revisions (M3), session events.

## Who is the author

Tailscale authenticates the login behind every request:

- proxied through Tailscale Serve: the `Tailscale-User-Login`;
- direct loopback request: the machine owner's login, or `local` when Tailscale cannot tell.

A request without more is made by that human (`HUMAN` author). An agent acting through the login adds `Prunelle-Agent: <harness>:<session-id>` (the CLI sends `$PRUNELLE_AGENT`); its changes are authored by that `AGENT`, and the event log keeps the login. The agent name is declared, not verified: an agent can never write as another human. Only humans submit decisions. Manifest imports keep their declared author; the import event records the caller.

## Data model (migration 3)

- `topics.version`, `representations.version`: integer, starts at 1, incremented by every change (including position shifts caused by a sibling's move).
- `discussions`: review, revision the anchor was made against, anchor type, one nullable foreign-key column per anchor target (`topic_id`, `intent_id`, `change_id`, `finding_id`, `evidence_id`, `representation_id` + `element_id`), a CHECK tying each column to its anchor type, status `OPEN`/`RESOLVED`, author, version, timestamps. Same pattern as `attention_signals`.
- `discussion_code_ranges`: like `evidence_code_ranges` (repository, path, side, lines, blob hash, selected text).
- `discussion_messages`: discussion, author, body, created at. Immutable.
- `decisions` (`COMMENT`/`APPROVE`/`REQUEST_CHANGES`, review, revision, author, body, created at) with `decision_findings` and `decision_discussions`. Immutable.
- `events`: `sequence INTEGER PRIMARY KEY AUTOINCREMENT`, type, entity ID, review ID, actor, occurred at.
- `idempotency_keys`: caller, key, request hash, response status/headers/body (null while running), created at.

## Anchors

| Type | Target |
| --- | --- |
| `REVIEW` | the review itself |
| `TOPIC`, `INTENT`, `CHANGE`, `FINDING`, `EVIDENCE` | a record of the same review |
| `CODE_RANGE` | repository, path, side, lines of a changed file in the anchor's revision; the server resolves the blob hash and selected text, exactly as for code-range evidence |
| `DIAGRAM_ELEMENT` | a diagram representation of the review and one of its node IDs |

The spec's `COMPONENT`, `USER_FLOW_STEP`, `DESIGN_ELEMENT` have no records to point at yet and are left out. The anchor revision defaults to the review's current revision.

Each discussion lists `topic_ids`, computed on read, so a topic view shows every discussion about it whatever block created it (acceptance criteria 3, 4): the topic itself; topics linking the intent, change, or finding; topics reaching the evidence; the diagram's topic; for a code range, the topics owning that file under the canonical topic→file rule.

## Rules

- **Topics.** Create (`MANUAL`, appended last among siblings), edit title/summary/state and replace link sets, move to a parent and position (siblings renumbered, no cycles, same review). Linked records must belong to the review. `OBSOLETE` topics no longer claim files, so their code shows up as unassigned rather than hidden.
- **Representations.** Create (`MANUAL`) and edit title/config with record IDs instead of manifest keys. The same structural checks as imports (sections, nodes, edges, code-diff evidence must be code ranges); references must belong to the review.
- **Discussions.** Created with an anchor and a first message. Replies bump the discussion version. Status `OPEN` ↔ `RESOLVED`.
- **Decisions.** Tied to a revision of the review (default current). `COMMENT` needs a body. `REQUEST_CHANGES` selects at least one finding or discussion of the review; other decisions select none. Never modified.

## HTTP

```text
POST   /v1/reviews/{id}/topics                       create topic
PATCH  /v1/topics/{id}                               edit topic                 If-Match
POST   /v1/topics/{id}/move                          move topic                 If-Match
POST   /v1/topics/{id}/representations               create representation
PATCH  /v1/representations/{id}                      edit representation        If-Match
GET    /v1/reviews/{id}/discussions                  discussions with messages
POST   /v1/reviews/{id}/discussions                  create discussion
GET    /v1/discussions/{id}
PATCH  /v1/discussions/{id}                          resolve / reopen           If-Match
POST   /v1/discussions/{id}/messages                 reply
GET    /v1/reviews/{id}/decisions
POST   /v1/reviews/{id}/decisions                    submit decision
GET    /v1/events?after=N                            SSE
```

- **Concurrency.** Mutable resources expose `version` in their body and `ETag: "<version>"` on single-resource responses. Updates require `If-Match`: missing → `428 PRECONDITION_REQUIRED`, stale → `412 PRECONDITION_FAILED`.
- **Idempotency.** Every `POST` that creates something accepts `Idempotency-Key` (capture, import, workspace, review, topic, representation, discussion, message, decision). The key is claimed before the request runs, scoped to the caller, kept 24 h. Same key and same request → the stored response, with `Idempotent-Replayed: true`. Same key, different request → `409`. Key still running, or its request was interrupted by a crash → `409` (outcome unknown; refetch). Failed requests release the key.
- **Events.** Each mutation appends an event in its own transaction: `workspace.created`, `review.created`, `revision.created`, `import.created`, `topic.created|updated`, `representation.created|updated`, `discussion.created|updated` (a reply updates its discussion), `decision.created`. An event names the entity, its review, and the actor; clients refetch the entity. `GET /v1/events` streams events after `after` or `Last-Event-ID` (default: from now), starting with a `ready` event carrying the current sequence; a keepalive comment every 20 s. Commits wake streams; streams read from the database, so nothing is lost across reconnects or restarts.
- **Durability.** SQLite `synchronous=FULL`, so an acknowledged comment survives a machine crash, not only a process restart.

## CLI

`prunelle events [--after N]` prints the stream as JSON lines. Other mutations go through the API (`curl` on loopback needs no credentials); the M2 client is the editing UI.

## Tests

- Review service: topic CRUD, move renumbering and cycle rejection, foreign IDs rejected, obsolete topic files unassigned, representation validation, every anchor type, code-range resolution and bounds, `topic_ids` derivation, replies, resolution with stale version, decision rules, events written in the mutation's transaction.
- API (responses validated against `openapi.yaml`): `ETag`/`If-Match` (`428`, `412`), idempotent replay and key reuse, SSE delivery, resume with `Last-Event-ID`, and a restart (server and database reopened on the same directory) with discussions, decisions, events, and idempotent replays intact.

## Implementation notes

- New `internal/events` package: `Append` inside the mutation's transaction, `After`/`Head` for readers. `store.DB.Changed()` returns a channel closed by the next commit; event streams wait on it and then read the database.
- The stream is served through the generated strict handler with a custom response type, so it can flush. Streams also end when the server's context is cancelled, so shutdown does not wait 10 s for them; ordinary requests keep their own contexts and finish during the graceful shutdown.
- Replies emit `discussion.updated` rather than a `message.created` event: an event names the resource to refetch, and a message is read through its discussion.
- `review.RepresentationConfig` is now one embedded type shared by the read model, the create/update requests, and the import path; imports and manual edits run the same structural checks.
- `reviewRecords` indexes a review's record IDs inside the write transaction; topic links, representation references, anchors, and decision selections are checked against it.
- Code-range resolution (`resolveCodeRange`) is shared by evidence imports and code-range discussions.
- Existing write paths (workspace, review, capture, import) gained an actor parameter and an event.

## Decision ledger

Choices made where the spec and plan were silent, least confident first.

1. **Agents name themselves with a `Prunelle-Agent` header** (agreed with you: Tailscale authenticates, agents add a header). Only the event log records the login an agent acted through, not each record. Agent names are free-form, e.g. `pi:<session-id>`; how Pi exposes its session ID to its tools is not checked yet.
2. **`REQUEST_CHANGES` must select at least one finding or discussion, and other verdicts select none; `COMMENT` needs a body.** *Would have asked:* is a request for changes with only a free-text body acceptable?
3. **`If-Match` is required on every update** (428 without it), not merely honored when present.
4. **Sessions emit no events yet.** Runtime state changes come from the observer, not from users; the M2 session panel can poll `GET /v1/runtime-sessions` or a later change can add `runtime_session.updated`. *Would have asked:* does the session panel need live updates in M2?
5. **`OBSOLETE` topics claim no files**, so marking a topic obsolete moves its exclusive files to Unassigned. Discussions still list an obsolete topic they are anchored to.
6. **A failed request with a 5xx keeps its idempotency key claimed** (outcome unknown) until it expires after 24 h; only 4xx releases it. Keys are scoped to the caller's login.
7. **A move changes the version of every sibling whose position shifts**, so a stale client cannot overwrite positions it did not see.
8. **A reply changes the discussion's version**, so resolving a thread asks for a reload if someone replied in between.
9. **Anchor types `COMPONENT`, `USER_FLOW_STEP`, `DESIGN_ELEMENT` are left out**: no records exist for them. A code-range anchor must target a changed file, like code-range evidence.
10. **Representations: several of the same type are allowed per topic**, the revision stays the one current at creation when edited, and no deletion. Topic `title` cannot be blank; `summary` can.
11. **Messages and decisions are immutable**; replies do not reopen a resolved discussion.
12. **Event payloads name the entity, review, actor, and time only**; clients refetch. Events are kept forever.
13. **SQLite `synchronous=FULL`** instead of `NORMAL`, at the cost of one fsync per commit.
14. **`prunelle events` is the only new CLI command**; mutations go through the API.

## Verification

- `gofmt`, `go vet`, stable `go generate`, `go test -race ./...`, `GOOS=darwin GOARCH=arm64 go build`: pass.
- Mutation checks: disabling the version comparison, the obsolete-topic filter, the commit notification, idempotent replay, key release, gap closing on move, code-range topic derivation, or `Last-Event-ID` handling each makes a test fail.
- Manual, built binary on a scratch data directory: fixture seeded; a discussion posted twice with the same `Idempotency-Key` (second response replayed); `PATCH` without `If-Match` → 428, with `"1"` → 200 and `ETag: "2"`; a `REQUEST_CHANGES` decision attributed to this machine's Tailscale owner; `prunelle events --after 0` printed all seven events in order; the server stopped in 0.05 s with the stream open; after restart the discussion, its derived `topic_ids`, the idempotent replay, and the unassigned count (obsolete topic) were intact.
- **Not verified:** event streaming through a real `tailscale serve` proxy (buffering, idle timeouts); a machine crash (durability relies on `synchronous=FULL`).
