# Server-side Pi comment queue

Status: implemented locally on `simplify-pi-comments`, following [comment simplification](pi-comments.md). D14 supersedes the previous busy/unsent, no-queue behavior. Not deployed or published.

## Accepted behavior

- Prunelle owns a durable FIFO queue **per Pi conversation across reviews**. The extension executes one request, answers normally and reports settled readiness; it owns no queue.
- Desktop comment/reply posting saves first, then requests an answer. A selected Pi accepts DISCUSS while busy, offline or paused. No selected Pi leaves the saved comment unsent; attachment alone never sends existing comments.
- Only never-dispatched comments can be cancelled. Cancellation retains the discussion/message. Already-dispatched work is never automatically replayed.
- An uncertain dispatched outcome pauses the queue. Inspect Pi and explicitly resume pending comments; late results, reconnect and startup do not acknowledge uncertainty for the user.
- Generation and implementation remain separate explicit, immediate-only requests; they cannot bypass a paused/nonempty comment queue. Normal Pi permissions and the separate saved REQUEST_CHANGES authorization boundary remain unchanged.

## Implementation

`server/internal/review/agent_queue.go` owns durable ordering/claims, startup recovery, cancellation and queue pause. Migration 0008 extends invocation states with QUEUED/CANCELLED and stores pause/version on the logical Pi identity; released migrations are untouched. A transaction claims the oldest queued comment only if the queue is unpaused, no invocation remains PENDING/RUNNING, and its review still selects the same Pi. The claim records actual connection/model/context and refreshes the prompt using the original stored anchor and message. Exact selected lines only; no neighboring source is added.

`server/internal/agents/queue.go` coordinates that durable state with the existing live connection slot. Enqueue, readiness, cancellation, binding changes and deletion trigger the same dispatcher. Completion alone does not release the slot: Pi must also report settled readiness. Post-commit dispatch is bounded independently of the initiating HTTP request’s cancellation, so closing the desktop cannot revoke an accepted enqueue. No polling worker, execution replay, lease or automatic write retry was added.

Startup converts PENDING/RUNNING to UNKNOWN and pauses their conversations; QUEUED remains untouched. Migration also initially pauses conversations with pre-existing schema-7 UNKNOWN results, without rewriting those records. A human acknowledgement remains effective across later restarts even if the old UNKNOWN record remains. Human resume uses a quoted queue version in If-Match, protecting against acknowledgement of a newer uncertain outcome by an older control. Changing the review’s selected conversation cancels its unsent entries transactionally; it never redirects them. Deletion uses existing ownership cleanup, removes that review’s entries/receipts and rejects late publication, without changing other reviews or live Pi processes/history.

API additions:

- `GET /v1/agent-sessions/{id}/queue`: outstanding requests across reviews in acceptance order, including UNKNOWN history awaiting inspection.
- `POST /v1/agent-invocations/{id}/cancel`: human-only, repeat-safe cancellation of QUEUED work.
- `POST /v1/agent-sessions/{id}/resume-queue`: human-only conditional resume, not replay of UNKNOWN work.

The desktop shows queued status/cancellation beside comments and the selected Pi’s cross-review queue under Settings → Integrations. Only the selected conversation exposes resume, alongside its inspectable queue. Direct API message writes remain storage-only; CLI `agent ask` explicitly submits to the same server queue. The extension wire protocol remains unchanged.

## Decisions where the request was silent — least confident first

1. **Selection changes cancel, not retain or redirect, unsent work.** This avoids background execution in a conversation the review no longer selects. Includes automatic selection changes; comments remain available for deliberate resubmission. Would ask: should switching Pi instead leave the old conversation’s queue running?
2. **Offline/paused selected Pi still accepts comments; missing selection does not.** Accepted entries retain that exact target across desktop closure/restart. Would ask: should offline enqueue require an extra confirmation?
3. **Persist pending comments through server restart; pause only when dispatched execution is uncertain.** Include pre-upgrade UNKNOWN history in the initial pause, not just requests interrupted during upgrade. Never-dispatched work can proceed when the same Pi reconnects ready. A crash between durable claim and wire delivery is conservatively UNKNOWN, never replayed. Would ask: should even never-dispatched work require a restart confirmation?
4. **Generation/implementation remain immediate-only and cannot overtake pending comments.** Only DISCUSS is queued; UNKNOWN pauses all new execution until human acknowledgement. Definite FAILED results allow subsequent queued comments after readiness. Would ask: should other intents eventually join this queue?
5. **Resume acknowledges uncertainty without rewriting history.** UNKNOWN stays visible until a matching late result arrives; late completion does not itself unpause. Cancellation cannot stop active Pi. Resume is conditionally versioned and never retried automatically. Would ask: should acknowledged UNKNOWN history be hidden from the outstanding list?
6. **FIFO means server transaction acceptance across reviews.** SQLite insertion order is the canonical ordering; no timestamps, client order, priority, reorder control or extra sequence field. Model/context/connection are captured at dispatch, allowing the existing conversation to advance while comments wait. Would ask: should model selection be pinned when enqueued instead?
7. **Reuse invocation persistence and connection events, not an extension queue or separate worker.** Existing receipts make ambiguous enqueue retry safe with the same key; save and enqueue remain separate, so interrupted posting can leave a saved/unsent comment. Initial DISCUSS receipt is QUEUED even if dispatch immediately follows; current state comes from queries/SSE. Would ask: should comment save and enqueue become one atomic API operation in a future change?
8. **Preserve old committed registration bytes.** Queue fields are always present on fresh session responses but optional in OpenAPI because real pre-upgrade registration receipts omit them. No rewriting of receipts or compatibility transport was added. Would ask: none; preserving committed replay is an existing requirement.
9. **Keep visibility in existing surfaces.** Inline cancellation plus a selected-conversation queue in Settings, not a new global dashboard or CLI command family. Cross-review entries show canonical review/request IDs and the saved prompt. Would ask: should queue inspection later have a dedicated global page?
